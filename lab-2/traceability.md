
# Лабораторна робота №2 — Матриця трасування

## 1. Призначення

Матриця трасування встановлює зв'язки між функціональними вимогами EARS (REQ), групами Gherkin-сценаріїв (SC) та Use Cases (UC).

Одна група сценаріїв може перевіряти кілька вимог, а одна вимога може перевірятися кількома групами сценаріїв.

Нефункціональні вимоги NFR не включаються до цієї матриці, оскільки перевіряються окремими тестами якості.

## 3. Приклади трасування багато-до-багатьох

**Одна вимога — кілька груп сценаріїв:**

- REQ-03 перевіряється у SC-02 та SC-06.
- REQ-05 і REQ-06 перевіряються у SC-03 та SC-06.
- REQ-09 перевіряється у SC-02 та SC-06.

**Одна група сценаріїв — кілька вимог:**

- SC-02 перевіряє REQ-03, REQ-04, REQ-09 і REQ-11.
- SC-03 перевіряє REQ-05, REQ-06, REQ-12, REQ-13, REQ-14 і REQ-15.
- SC-06 перевіряє REQ-03, REQ-05, REQ-06, REQ-09 і REQ-12.
- UC07 «Завершити покупку» включає UC03 «Оформити замовлення» та UC04 «Оплатити замовлення» через зв'язки `include`. Вимоги REQ-03, REQ-05 та REQ-12 відображають основні етапи завершення покупки.


UC04 «Оплатити замовлення» деталізований п'ятьма Gherkin-сценаріями в SC-03: ініціювання, успішне підтвердження, відмова, повторне підтвердження та повторна оплата.

## 4. Перевірка повноти

Усього функціональних вимог: **15**.

Покрито Gherkin-сценаріями: **14**.

Не покрито: **1** (REQ-10).

Нефункціональних вимог: **6** (NFR-01–NFR-06), вони не входять до матриці.


У Use Case Diagram визначено **7 Use Cases** (UC01–UC07). Усі вони пов'язані принаймні з однією функціональною вимогою.


## 5. Непокрита вимога

**REQ-10 — повернення коштів.**

Повернення коштів не входить до базової версії онлайн-магазину. Відповідний Gherkin-сценарій та Use Case не створено.

Для майбутньої реалізації потрібно уточнити правила повернення, допустимі статуси платежів та взаємодію із зовнішнім платіжним сервісом.

## 6. Узгодженість із ER-моделлю

| Вимоги | Сутності ER-моделі |
|---|---|
| REQ-01, REQ-02 | Product, Category |
| REQ-03, REQ-04, REQ-09, REQ-11 | Customer, Order, OrderItem, Product |
| REQ-05, REQ-06, REQ-12, REQ-13, REQ-14, REQ-15 | Order, OrderItem, Payment |
| REQ-07 | Product, Category |
| REQ-08 | Order |
| REQ-10 | Payment — майбутнє розширення |

Для збереження історичної ціни використовується OrderItem.unit_price. Для одного Order допускається не більше одного Payment.

Адміністратор і платіжний сервіс є зовнішніми акторами взаємодії, а не окремими сутностями ER-моделі.
