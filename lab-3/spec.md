
# Лабораторна робота №3 — Специфікація Sequence-діаграм

## 1. Обраний Use Case

UC04 — «Оплатити замовлення».

Предметна область — онлайн-магазин.

Мета UC04 — забезпечити ініціювання оплати замовлення, отримання результату від зовнішнього платіжного сервісу та коректне оновлення даних про оплату.

## 2. Джерело сценаріїв

Для деталізації використано SC-03 із лабораторної роботи №2.

Розглянуто п'ять сценаріїв:

1. Ініціювання оплати.
2. Успішне підтвердження оплати.
3. Відмова платежу.
4. Повторне підтвердження платежу.
5. Спроба повторної оплати сплаченого замовлення.

## 3. Учасники взаємодії

- Покупець (Customer) — ініціює оплату.
- Вебінтерфейс (UI) — приймає дії покупця та відображає результат.
- Сервіс оплати (PaymentService) — перевіряє стан замовлення й обробляє платежі.
- База даних PostgreSQL (DB) — зберігає Order, OrderItem і Payment.
- Зовнішній платіжний сервіс (Gateway) — приймає платіжні запити та надсилає результати.
- Сервіс сповіщень (NotificationService) — повідомляє покупця про невдалу оплату.

PaymentService, UI, Gateway та NotificationService є компонентами або зовнішніми сервісами, а не новими сутностями ER-моделі.

## 4. Кроки сценаріїв

### Сценарій 1. Ініціювання оплати

1. Покупець ініціює оплату замовлення.
2. Система отримує Order та OrderItem.
3. Перевіряє статус замовлення і можливість оплати.
4. Обчислює суму за кількістю та збереженою ціною позицій.
5. Передає ідентифікатор замовлення та суму платіжному сервісу.
6. Повертає покупцю результат ініціювання.

### Сценарій 2. Успішне підтвердження

1. Платіжний сервіс надсилає повідомлення про успіх.
2. Система перевіряє автентичність повідомлення.
3. Отримує поточні дані Order і Payment.
4. Зберігає Payment зі статусом success.
5. Встановлює Order.status у paid.
6. Підтверджує обробку повідомлення.

### Сценарій 3. Відмова платежу

1. Платіжний сервіс надсилає повідомлення про відмову.
2. Система перевіряє автентичність повідомлення.
3. Отримує дані Order і Payment.
4. Зберігає Payment зі статусом failed.
5. Залишає Order.status рівним pending.
6. Повідомляє покупця про невдалу оплату.

### Сценарій 4. Повторне підтвердження

1. Платіжний сервіс повторно надсилає підтвердження.
2. Система перевіряє автентичність повідомлення.
3. Виявляє, що Payment уже має статус success.
4. Не створює другий запис Payment.
5. Залишає Order.status рівним paid.
6. Підтверджує обробку повторного повідомлення.

### Сценарій 5. Повторна оплата

1. Покупець повторно ініціює оплату.
2. Система отримує Order зі статусом paid.
3. Виявляє, що замовлення вже оплачене.
4. Відхиляє повторну оплату.
5. Не надсилає нового запиту зовнішньому платіжному сервісу.

## 5. Узгодженість із ER-моделлю

Використовуються сутності Order, OrderItem та Payment із лабораторної роботи №1.

Сума оплати обчислюється за OrderItem.quantity та OrderItem.unit_price.

Для одного Order допускається не більше одного Payment.

Успішна оплата змінює Order.status на paid, а відмова залишає pending.

## 6. Межі деталізації

Sequence-діаграми описують лише UC04 «Оплатити замовлення».

Створення товарів, керування каталогом, доставка та повернення коштів не розглядаються.
